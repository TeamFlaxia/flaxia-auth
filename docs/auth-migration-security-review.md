# Auth migration security review

Status: **release blocking**. This engineering review does not substitute for independent review or production verification.

## Findings and current mitigations

1. **Credential and Vault coordination.** Auth owns the password verifier and the encrypted Vault envelope. A password change carries an opaque `vault_kek` rewrap, and Auth commits the verifier, the VK rewrap and the item-version bump in one D1 transaction. A stale `vk_version` fails without changing either side, and missing rewrap is rejected with 409. Flaxia can access the same store through the grant-bound `/api/flaxia/vault` bridge. Rows still stored in Flaxia D1 are copied once through the grant-bound `/api/flaxia/vault/import`; the import validates only envelope/row shapes and limits, is idempotent on an identical envelope, and refuses (409) to replace a different existing envelope. The source rows are deleted only after Auth confirms the same envelope.
2. **Identity binding.** An existing profile is linked only after credential proof; a new profile uses the authenticated Auth ID. Matching a username or email alone never links existing profiles. The operational migration must handle collisions and users unable to establish a link.
3. **Deletion.** An Auth SRP proof authorizes deletion; the application stores only an operation hash and completes cleanup from an Auth receipt. Browser retries and the scheduled application worker resume interrupted cleanup. Cancellation tombstones prevent delayed deletion after rejection. Content-addressed profile images are queued only after their last user reference disappears, and a claimed R2 outbox retries failures while preventing new references. Verify scheduled-worker deployment and review receipt retention and historical unreferenced objects.
4. **Account recovery and migration coverage.** Auth supports an independent, browser-generated 256-bit recovery code using SRP; only its salted verifier is stored. Enrollment requires the current password. Enrollment or replacement revokes other Auth sessions and outstanding recovery handshakes. Successful recovery also revokes existing sessions and password login handshakes before issuing a new session. Recovery can reset the password while the browser separately uses the Vault recovery phrase to rewrap the Vault key. Existing users must enroll a recovery code before losing their password. Accounts whose pre-migration credentials cannot be matched still need a separately verified identity-linking process; do not enable authority mode globally until those accounts are resolved. Neither recovery code nor Vault phrase is sent to a server.
5. **Legacy fingerprints.** Password-derived fingerprints are deleted on completed linking, credential change or account deletion and expire after at most 90 days. They can enable offline guessing if Auth's DB is exposed. Backups may restore expired rows: purge before restoring service and follow [flaxia-migration.md](flaxia-migration.md).
6. **Grant storage.** Direct mode keeps the opaque grant in an HttpOnly browser cookie; Auth stores its hash. Transitional legacy integration still stores grants and copied verifiers in Flaxia until accounts are switched and purged. The short-lived multiplayer ticket cache also contains the session token; review its access and retention.
7. **Email change.** Direct mode reserves the application address before an SRP-protected Auth update and reconciles the application profile from a hashed Auth receipt. Email is unverified and must not be used as an account recovery factor. Test ambiguous failures and address races against D1 before rollout.

Auth rejects API mutations without an allowed Origin and Cloudflare client IP. Each API path has an IP rate limit; recovery start and verify also have a 10-per-minute IP limit, and recovery start has a 5-per-minute username limit. The fake recovery challenge keeps the response shape consistent for missing users and factors. Rate limits reduce guessing and denial-of-service pressure but still depend on Cloudflare preserving `CF-Connecting-IP` at the Worker boundary.

Both PRs should remain draft until account recovery, operational migration, independent review, and production deployment prerequisites are complete.
